# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Alias Quick Switcher matches a path-shaped query segment by segment, where each segment may be satisfied by a real name **or** by an alias — the note's own aliases for the leaf, and the alias on a folder's folder note for an ancestor. Obsidian's built-in switcher scores a candidate as `max(fuzzy(query, path), fuzzy(query, alias))`, so path and aliases are separate match targets that are never combined; that is precisely the gap this plugin closes.

Measured against a real Obsidian 1.13.7 over CDP before any code was written: `Alpha/Bravo/Charlie`, `Alpha Bravo Charlie`, `Bravo Charlie` and `Echo` all match `Alpha/Bravo/Charlie.md`; `Alpha/Bravo/Echo`, `Alpha/Delta/Charlie` and `Alpha/Delta/Echo` return an empty list.

## Architecture

Two headless layers, an index component, and a modal. The headless layers carry all the correctness risk and are unit-testable with no DOM and no `App`.

- `src/segment-matcher.ts` — a DP over (query token × path position). `/` is a hard segment boundary, whitespace a soft one; a position may absorb several whitespace-joined tokens, and positions may be skipped so a partial path matches. Returns a score **and** which label satisfied each position.
- `src/ranking.ts` — the comparator that orders matched candidates, in either of the two `RankingMode`s.
- `src/label-index.ts` — `folderPath → labels` and `filePath → labels`, memoized on first use. Each label is stamped with where it came from, which is what the row's flair reads.
- `src/label-index-component.ts` — the index's lifecycle: it invalidates on `metadataCache` `changed` and the vault's create/rename/delete, and once per switcher open re-reads the title properties from Advanced Metadata Cache and re-resolves the folder-note setup.
- `src/advanced-metadata-cache.ts` — this plugin's compiled-against declaration of the dependency's API: the id, the version range, and the two narrow consumer contracts (the title read, the settings handover).
- `src/alias-quick-switcher-modal.ts` — `extends SuggestModal`, following `obsidian-link-picker`'s `LinkPickerModal`.

### Why the DP carries four things in its state, not two

Two of the ranking keys are not decided at the cell where the choice is made: whether a skipped position counts as a GAP depends on whether anything is consumed after it, and the tier depends on the leaf and the ancestors together. So the state is `(tokenIndex, positionIndex, pendingSkipCount, wasAncestorAliasUsed, leafKind)`. With those in the state every remaining key is additive or prefix-monotone, which is what makes keeping only the best prefix per state safe. Collapsing the state back to `(tokenIndex, positionIndex)` silently returns a worse match rather than failing.

## Invariants that are easy to break

- **Never patch the built-in switcher.** A separate command is the whole interaction contract with the user (decision recorded 2026-08-30). Registering a second entry point, rebinding `Ctrl+O`, or monkey-patching `switcher.instance.onOpen` is a takeover by the back door.
- **Advanced Metadata Cache is a HARD dependency, and the title properties are ITS setting, read live.** Declared through `getPluginDependencies()`, so `onloadImpl` does not run while it is missing. The reason is not the property: this plugin's whole performance story is a lookup index, and that plugin exists to keep metadata lookups indexed — a cache for a cache (owner decision, 2026-09-09). `LabelIndexComponent.refresh()` reads `getTitlePropertyNames()` through `watchPluginApi` on every switcher open and hands the list to `LabelIndex`, which reads the VALUES off the frontmatter itself. `getTitles(file)` is deliberately not used: it returns bare strings, and the flair needs to know which property each value came from. The `names` index is not used either — it is eager and reverse, and this plugin needs a lazy, forward, folder-aware answer. Never reintroduce a property-name setting here: two places to type `title` is the outcome the move exists to prevent.
- **The retired `extraLabelPropertyName` is parked, never dropped.** A legacy converter in `PluginSettingsComponent` moves a non-empty value into `proposedTitlePropertyName`, and a `SettingsMigrationComponent` offers it to Advanced Metadata Cache as `{ titlePropertyNames: [value] }`, clearing it only when the user applies the migration there. It watches with the consumer contract `{ migrateSettings: {} }`, which Advanced Metadata Cache 1.0.0 does not publish — so against that release the offer is silent and the value simply waits. Do not widen the dependency's own range to require `migrateSettings`: that would refuse to run on every provider that exists, to carry one optional string.
- **Do not cut a release carrying the dependency until Advanced Metadata Cache is listed in the community directory.** The dependency gate's one-click repair installs from the community registry by plugin id, so a release shipped before that listing leaves every existing user with a plugin that refuses to start and a repair button that finds nothing.
- **The folder-note answer comes from obsidian-dev-utils, live.** `FolderNoteLocation.Auto` reads the installed `folder-notes` plugin's own settings at every use, and `LabelIndexComponent.refresh()` re-resolves it on every switcher open. Do not copy those values into this plugin's settings — a copy goes stale the moment that plugin is reconfigured, and it would need a migration to seed.
- **Real names outrank aliases — under the DEFAULT ranking.** `RankingMode.Tiered` is what makes the plugin never reorder the matches the built-in already produces, and it is the default for that reason. `RankingMode.LinkPicker` deliberately trades that guarantee for surfacing alias hits sooner. Changing which one is the default changes a promise the README makes.
- **Show which label satisfied each segment.** A row matched via `Alpha/Delta/Echo` displays that rendering, with the real path beneath it. The second line is compared against the candidate's PLAIN rendering, not against its path: the path carries an extension and the rendering never does, so comparing the two puts a redundant second line under every row.
- **The row is the BUILT-IN switcher's shape, measured off it rather than guessed at.** Obsidian already renders a leaf-alias hit, and `src/builtin-comparison.desktop-capture.integration.test.ts` puts the two side by side. Its markup is `suggestion-item mod-complex` > `suggestion-content` > `suggestion-title` + `suggestion-note`, with `suggestion-aux` > `suggestion-flair[aria-label="Alias"]` carrying a `lucide-forward` icon; the note line drops the markdown extension. This plugin uses all of it. Do not reintroduce private class names for these: Obsidian and every community theme style the built-in's classes, and a private copy gets no theme support at all — the stylesheet is 336 bytes because of this, and the only rule left in it is the folder icon, which the built-in has no equivalent of.
- **The flair says WHICH kind of name matched, and that is the ONLY thing allowed to notice the difference.** `Label.source` is a discriminated union — real name, alias, or a frontmatter property carrying its key — and three jobs read it. Two of them must never tell an alias from a property: the DP's `leafKind` / `wasAncestorAliasUsed`, and `checkIsLeafOnlyAliasMatch`'s choice of row shape. Both go through `checkIsAliasLike`, so a title-satisfied position ranks and renders exactly as an alias-satisfied one does, and widening either would silently move a row into a different `MatchTier`. The third job is the flair, and it is the reason the source is payload rather than a fourth dimension of the DP state: a purely presentational distinction must not buy one.
- **The two glyphs are Obsidian's own property iconography, not a choice.** `lucide-forward` is what Obsidian draws beside the `aliases` property type in its Properties UI (and on an alias hit in its own switcher); `lucide-text` is what it draws beside the `text` type, which is what a title is. A user meets both before they ever open this switcher. One glyph covers EVERY configured property — arbitrary property names cannot map to meaningful glyphs — so the symbol answers alias-versus-property and the `aria-label` answers which property, naming the frontmatter key verbatim. That tooltip is readable on a phone too: Obsidian's trigger is `pointerover`, which a finger-down fires, with a 1000 ms delay and a `pointerup` teardown, so touch-and-hold shows it.
- **A row carries one flair per distinct source it was actually reached through, in path order** — so the markers read left to right in the same order as the labels they explain. Obsidian anticipates several flairs on one row and spaces them itself (`.suggestion-item.mod-complex .suggestion-flair:not(:last-child)` carries a `margin-inline-start`), which is why this needs no rule in the 336-byte stylesheet. Showing only one would hide the property hit on exactly the row that needs both, which is the case the distinction exists for.
- **`IconName` is unconstrained in the typings, so a misspelt icon id ships as a BLANK flair.** It compiles, and the mocked `setIcon` resolves nothing, so no unit test can catch it. `src/source-flairs.desktop.integration.test.ts` asks a real Obsidian's `getIconIds()` and reads the rendered `svg`'s class off the row; keep both halves if the markers ever change.
- **A leaf-only alias hit renders the alias ALONE.** That is the one match the built-in also makes, and rendering the whole path there would put `Alpha/Bravo/Echo` over `Alpha/Bravo/Charlie` — two strings one word apart, where the second line earns its space least. The full as-matched path is reserved for a hit that reached an ANCESTOR, which is the thing no other switcher can show. `isLeafOnlyAliasMatch` reads `match.positions`, not the candidate's, so a leaf satisfied by its real name is not caught by it.
- **Resolving a folder note never creates one.** A folder with no folder note is simply not offered.
- **A folder note is reachable twice on purpose** — as a file by its own name, and as its folder by the folder's name — so that both `Alpha/Bravo/Bravo` and `Delta` keep working. Only the ROWS are collapsed, by open target, after sorting.

## Performance, and why it is a first-class constraint

Measured on the vault this plugin was written for: 36,315 notes, 18,763 folders, 15,085 notes carrying `aliases`, and only 1,715 folders with a folder note. Three consequences the implementation must not undo:

- "Only scan aliased notes" is **not** a useful prefilter — 42% of notes are aliased.
- 91% of ancestor positions have exactly one label, so the segment walk usually has no branching. Anything that makes every position do folder-note work per keystroke throws that away.
- The label index memoizes lazily and is invalidated by events, so `resolveFolderNote` is called once per folder per switcher session — never per candidate per keystroke. `label-index.test.ts` asserts this by counting `resolveName` calls, and `switcher-latency.desktop-performance.integration.test.ts` measures the result at scale.

## Testing notes

- **Every integration vault is seeded with Advanced Metadata Cache's RELEASED build, pinned** (`scripts/helpers/advanced-metadata-cache-seed.ts`, downloaded once into the gitignored `.cache/`), and enabled after this plugin, so every run also drives the gate opening live. Without it every suite meets this plugin blocked and fails on something unrelated to what it tests. No `data.json` is seeded: that plugin's defaults leave the Titles module off, which is the aliases-only vault these suites were written against, and a suite about title properties switches the module on itself and puts it back. The unit tests stand in for the provider by publishing an API into the registry with `publishPluginApi`.
- The published `obsidian-test-mocks` has no `plugins` member on its strict `App`, and `resolveFolderNoteConfig` reads it. Tests assign one before use, the same way `obsidian-link-picker` does.
- `MetadataCache.setCache__` fires a `changed` event carrying **no file**, an event shape the real `MetadataCache` never emits. Tests write into `metadataCache.cache__` directly and then trigger the event they are actually about, with the arguments Obsidian really passes.
- The mock's `MetadataCache` re-parses a file's content on the vault's `create` event, so a hand-written cache entry is overwritten by it. A test about creation creates a real file instead.

### The screenshot capture suites

`npm run capture:screenshots` drives the switcher in a real Obsidian and writes `images/screenshots/screenshot-desktop-N.png` (six frames) and `screenshot-mobile-N.png` (five), desktop leg first because both legs share one machine. They exist because the two-line row is the one thing no assertion can settle — whether it READS as an explanation — and they double as the community-store listing shots.

- The suites are named `*.desktop-capture.` / `*.android-capture.` so they match **none** of the standard project globs: capturing opens a window and leaves a modal on screen to photograph it, which is not something `npm run test:integration` should ever do.
- The mobile leg runs on the **`obsidian_screenshots`** AVD, 900x1600 at density 320 — exactly the size the store asks for, so no crop or rescale. The shared `obsidian_test` AVD cannot stand in: it is 1344x2992, and resizing it at runtime recreates the activity and with it the WebView the session is attached to.
- **`labelScreenshot` needs `sharp`**, an optional peer of `obsidian-integration-testing`. Without it every frame fails at the caption step with `Cannot find package 'sharp'` — after the capture itself succeeded, so the failure looks unrelated to what actually went wrong.
- **A query that matches every segment whole highlights the entire first line**, which makes the highlight indistinguishable from its absence. Frame 5 uses `Alp/Del/Ech` for that reason: partial runs put highlighted and plain text side by side in the same word.
- **The LAST frame of each leg is the only one taken under a non-default setting**, and it puts it back in a `finally`. Frames desktop 1-5 and mobile 1-4 are shot with Advanced Metadata Cache's Titles module off, which is what a fresh install has; the final frame switches it on, reading `title`, so one row carries an alias marker and a property marker together — the case the two glyphs exist for, and one no default-settings frame can show. Both legs therefore stage `title: India` on `Charlie.md` alongside its `Echo` alias, mirroring the demo vault's own fixture. A frame added after it inherits whatever it left behind, so keep the restore.
- **`labelScreenshot` draws its band across the bottom of the frame**, which on desktop is Obsidian's status bar but on a phone is the switcher's own search field — so the typed query is the one thing a mobile frame does not show in full. The rows above it are what the frame is evidence for; do not caption a mobile frame with something only the query could prove.
- **The mobile frames photograph the DEVICE, not the page, and are therefore not byte-reproducible.** All four show a focused search field, so all four are taken with the soft keyboard up. `captureObsidianScreenshot` cannot produce that: it drives Appium in the WebView context, so it captures the page, and the IME is a system window that is not part of the page — which left the lower 59–71 % of each frame as an empty band where a phone shows a keyboard. `captureDeviceScreenshot` reads the framebuffer instead, and brings the status-bar clock and battery indicator into the frame with it. That is the trade: a frame honest about the experience, at the cost of a re-capture never being byte-identical. Do not "fix" the churn by reverting to the page capture.
- **A mobile frame LOWERS the keyboard again when it is done, and that is what makes five frames possible.** `raiseSoftKeyboard` proves the lift as a DELTA against a baseline read just before its own touch, so a keyboard still up from the previous frame reads as a field that never moved: measured here on 2026-09-20 on `obsidian-integration-testing` 12.3.0, frame 1 passed and frames 2-5 each failed `the keyboard did not come up` with `lift=0` while the same message reported the device's own `mInputShown=true`, and the failure framebuffer showed a correctly lifted field under a fully drawn keyboard. So `shoot` presses `KEYCODE_BACK` after the capture and asserts the IME retracted — a showing IME consumes that key and the app never sees it, which is why it cannot close the switcher instead. The fix belongs behind the harness's API and is filed there; until it lands, do not "simplify" the retraction away, and do not replace it with teaching the suite to accept an unproved raise.
- **Raising the keyboard takes TWO things, and the harness owns both.** The AVD is built `hw.keyboard=yes`, so Android suppresses the on-screen keyboard entirely — `withSoftKeyboardEnabled` lifts that for the duration of a shot and restores the device exactly, *including* restoring a setting that had never been written, which takes a `settings delete` rather than a write. And a WebView does not ask for an IME on programmatic focus alone: `raiseSoftKeyboard` puts a real `adb` touch on the field, waits for the animation, and proves geometrically that the field lifted — nothing in the page reports the keyboard, so the field's own offset from the bottom is the only signal. A failure writes the device framebuffer and `dumpsys input_method` to `dist/screenshots/`, because a bare assertion failure here is unreadable.

### Writing a `*.cross-platform.*` suite here

The first constraint below was found the hard way, by every one of the eight suites failing on the first Android run after all eight passed on desktop. The second used to be a constraint of the same kind and is now a retired premise — kept because the shape it produced is still recognizable in this repo's history, and because reaching back for it is the mistake it warns against. The fourth is the last place that retired premise was still written down: every query-typing comment in these suites cited it until 2026-09-20, long after the gesture bullets had dropped it, which is how a merely stale comment outlives the sweep that retired its reason.

- **One `evalInObsidian` call is one `execute/sync`, and WebDriver caps a single script at 30 seconds.** A create-wait-open-type-assert flow fits inside that on a desktop and does not on a phone. Split the suite into several short calls and compute the stamp in the TEST, passing it in, so each call re-derives the same paths instead of carrying state across the boundary.
- **Trusted input reaches Android too — so dismiss a modal with Escape, and never with a tap on `.modal-bg`.** This bullet used to say the opposite: that `pressKey` reaches for `remote` and throws on a device, so a synthetic `.modal-bg` `.click()` was the one gesture that worked on both. The harness closed that gap — `obsidian-integration-testing` 12.0.0 gave the `lib` bag a mobile path through a CDP channel to the WebView, and 12.1.2 fixed it injecting each gesture once per attached host — so `pressKey`, `clickElement` and `clickMouse` all work on Android now, and every dismissal in these suites is `await pressKey({ key: 'Escape' })` inside a `pollInObsidian` `start` closure. Do not reach back for the background tap: a **trusted** tap is hit-tested at the element's centre, and `.modal-bg`'s centre lies behind the switcher, so the tap lands on the switcher and dismisses nothing. The old synthetic `.click()` only worked because it needs no hit test at all.
- **Picking a row is a trusted tap too — and `clickElement` hit-tests nothing, so the row's CENTRE has to be the row.** `src/open-switcher.cross-platform.integration.test.ts` drives the plugin's headline gesture with `await clickElement({ element: row })` rather than `row.click()`, so Obsidian's own hit-testing and click handling are what the suite exercises. `clickElement` computes the bounding-rect centre and taps it without checking what is there, which is the same hazard that makes `.modal-bg` unconvertible, only quieter: a scrollbar, a flair element or a row scrolled half out of the list would swallow the tap and leave the test asserting against a pick that never happened. The closure therefore asserts `document.elementFromPoint(centre)` is the row or a descendant and throws naming what covers it — keep that guard with any future conversion, because it is the only thing standing between this gesture and a silent pass. Measured green on both legs on 2026-09-20: nothing overlays the centre of the row the suite picks, on desktop or on the device.
- **Typing the query is the one gesture still DISPATCHED, and that is a measurement rather than an oversight.** Every suite here sets `.prompt-input`'s `.value` and fires `new Event('input', { bubbles: true })`. That shape is exempt from `no-untrusted-input-events` by construction - it notifies the app that the value changed rather than pretending to be a user - and nothing on the path gates on `isTrusted`: `SuggestModal` rebuilds its list from `input`, which is the only reason these suites assert anything at all. Converting it means a per-character `pressKey` loop, because the harness has no input-shaped batching helper: the `lib` bag's one text-entry member is `typeIntoEditor`, which takes a CodeMirror `Editor` and presses each code point via `pressKey` itself. Measured on this repo's own switcher, one stamped query per leg, 2026-09-20 on `obsidian-integration-testing` 12.3.0: **desktop 1.4 ms per character** (a 73-character query in 101 ms) against **Android 130 ms per character** (the same query in 12,125 ms), because the mobile seam is a round trip to the host per press. A single `evalInObsidian` is capped at ~30 s, so one converted query on the device would spend 40% of that budget on a warm emulator with the machine otherwise idle, and `alias-segment-matching` types eight of them. Do not convert on the strength of `isTrusted` alone: the mobile seam injects `Input.dispatchKeyEvent` over CDP into the WebView, so a converted suite would gain the full `keydown`/`keypress`/`beforeinput`/`input`/`keyup` pipeline and still never touch Android's IME, which is what a phone user actually types through. What would justify the cost is a plugin change that makes a KEY event matter here - suggestion navigation, a composition, a modifier - and then it is that behavior's own suite that should be trusted, not all eight.
  - **If a conversion is ever right, remember `pressKey` only QUEUES the press.** `sendInputEvent` returns before the renderer has processed anything, so reading `input.value` straight after the loop reads an EMPTY input. The first cut of the measurement above did exactly that and reported a plausible 0.94 ms per character for typing that had not happened - a converted closure has to wait for the value to land, which is one more wait inside the capped eval.
- **A timed-out closure wedges the shared WebDriver session**, so every suite after it fails in ~45 ms with no useful error. When a run collapses like that, re-run the first failing file alone before believing anything about the ones behind it.
- **A stale AVD boot snapshot kills the device mid-session — fixed upstream, and worth recognizing if it ever comes back.** The symptom: the emulator boots, serves adb, accepts a uiautomator2 session, and then goes `offline` about a minute later. Because the error reported depends on which call was in flight, one fault appears as a `POST /session` timeout, a `device offline`, or `Device ... was not in the list of connected devices` — which reads like four different problems. The cause was resuming a snapshot nothing had written: `obsidian-integration-testing` passed `-no-snapshot-save` without `-no-snapshot-load`, so every launch restored a `default_boot` that rots. Proof was one A/B — resumed died ~90 s in, `-no-snapshot-load` survived 240 s+. Since 12.1.0 the harness cold-boots by default, passing both flags, and snapshot reuse is an explicit opt-in that takes load and save together. If a run ever shows this again, check that nothing has re-enabled reuse before suspecting this repo.
- **A zombie `qemu-system-x86_64-headless` is the first thing to check when the Android leg will not start.** The harness launches with `-no-window`, whose backend process is `qemu-system-x86_64-**headless**.exe`; its teardown kills the launcher, logs `Killed auto-started emulator`, and leaves that backend alive holding TCP 5554/5555 and the AVD's `multiinstance.lock`. Every later run then refuses with `FATAL | Running multiple emulators with the same AVD` — on the emulator's own stdout, which the harness discards — and reports a `POST /session` timeout instead. Self-perpetuating, since each failure leaves another zombie. Confirm with `Get-Process | Where-Object { $_.ProcessName -like 'qemu*' }` (note that filtering on `qemu-system-x86_64` alone does NOT match it), recover with `Stop-Process -Force`, `adb kill-server`, and deleting `~/.android/avd/obsidian_test.avd/multiinstance.lock` — but not `hardware-qemu.ini.lock`, which is a directory healthy AVDs have too. - **A pre-booted emulator IS adopted — but only one whose console still answers.** The transport asks a running device `adb -s <id> emu avd name` and adopts it when the AVD matches, so starting the screenshots AVD by hand and then running the capture reuses it (measured 2026-09-12: the run logged no boot of its own and finished in 39 s instead of 105 s). What it cannot adopt is a **wedged** emulator, because a wedge blocks the console socket too — so that one question goes unanswered, the harness boots a second instance for the same AVD, and the collision surfaces as `Android emulator exited prematurely with code 1`. That error therefore means "the device that was already up is dead", not "do not pre-boot"; kill the wedged one rather than reaching for a flag.
- **`IntegrationSetupFailedError` is not a test failure and not a wedge — it is the Appium session never being created.** Every suite in the project fails in ~2 ms, the smoke test that only loads the plugin included, and the real error is one `WebDriverError: The operation was aborted due to timeout ... POST /session` far below the nine `FAIL` lines. If the smoke test is among the failures, read the setup error before reading anything else: no test ran, so nothing about the code is implicated. Seen when a capture run was still finishing on the same machine — a device leg and anything else heavy do not overlap.
- **`npm run test:integration` aborts at the first failing project, and the projects after it produce NO result.** The order is `no-app`, `demo-vault`, `android`, `desktop`, so an Android setup failure means the desktop suites never ran at all — their absence from the output is silence, not a pass. Count the `Test Files` blocks: four projects, four blocks. When the device leg is unreliable, run `test:integration:desktop` and `test:integration:android` separately so neither can hide the other.
